# Personal Finance App — Step 0 Specification

Sep 26, 2026

## 1. Product Purpose & Core Principles

**Purpose:** A Personal Financial Intelligence system, not just an expense tracker. It answers how much money exists, how much is truly spendable, where money is allocated, and whether spending, saving, and goals are on track, and why.

**Principles:**

- **Local-first.** All data lives in the browser via IndexedDB. No required backend. The app works offline.
- **Single-user.** No accounts, auth, roles, or multi-user architecture.
- **Financial Engine as source of truth.** All derived numbers are computed deterministically by the app itself, never by the AI layer.
- **Layered architecture:** Local Data, then Financial Engine, then Application/UI, then optional AI layer.
- **Data ownership.** The user can export, import, and migrate the complete dataset.
- **AI is optional and non-authoritative.** The app is fully functional with Gemini disconnected.

## 2. Finalized Entities & Fields

**Transaction** — id, type (income | expense | transfer), amount, date, categoryId (null for transfer), description, paymentMethod, createdAt, updatedAt. Income/expense carry assetId; transfer carries sourceAssetId and destinationAssetId instead. Optional sourceWishlistItemId (set on wishlist purchase) and recurringRuleId (set when generated by a RecurringRule).

**Category** — id, name, type (income | expense), parentId (optional), essential (bool), archived (bool), createdAt. Archived, never hard-deleted, once referenced by a Transaction or Budget.

**Asset** — id, name, type (cash | bank | savings | gold | other), liquidity (liquid | nonLiquid; default cash/bank/savings = liquid, gold/other = nonLiquid), openingBalance, openingBalanceDate, createdAt, updatedAt. openingBalance is the asset's balance at the start of openingBalanceDate; only Transactions dated on or after openingBalanceDate affect the calculated balance. There is no separately mutated balance field: for non-gold assets, currentValue is derived by the Financial Engine as openingBalance plus income minus expenses plus transfers in minus transfers out, computed from the Transaction ledger, which remains the sole authoritative record of money movement. Gold assets add karat; currentValue at a given date is derived as the applicable GoldHoldingRecord weight times the applicable GoldPriceRecord for that karat at that date (see GoldHoldingRecord, GoldPriceRecord, and Section 10).

**GoldPriceRecord** — id, karat, pricePerGram, effectiveDate, createdAt. A historical record, not a single latest-value field. The engine values a gold Asset by finding the applicable record for the requested karat and date, so historical net worth stays correct even after the price later changes. Manual entry only for the MVP; an automatic pricing API remains deferred.

**GoldHoldingRecord** — id, assetId, weightGrams, startDate, endDate (optional), createdAt. Time-aware, mirroring Allocation: a gold Asset's weight is never overwritten in place. If the owned weight changes (e.g. a sale), the existing record is closed with an endDate and a new record opens with the new weight and a matching startDate, so a September snapshot keeps using September's weight even after October's change. A GoldHoldingRecord is a recorded ownership state, not itself an income/expense Transaction; automatic linking between gold buy/sell actions and cash Transactions remains deferred.

**Allocation** — id, assetId, amount, goalId (optional), reason, startDate, endDate (optional), createdAt. Time-aware: an asset may have several Allocations, including historical ones closed with an endDate. Changing, reducing, releasing, or moving an allocation never mutates its history in place — it closes the existing record (sets endDate) and opens a new one with the updated amount/assetId and a matching startDate. This lets the engine answer both current-state and as-of-date questions (see Section 11).

**Goal** — id, name, targetAmount, deadline, priority, notes, createdAt. fundedAmount is derived as the sum of its Allocations, never manually edited. The engine computes progress percent, remaining amount, remaining time, required monthly contribution, current pace, projected completion date, and on-track status.

**WishlistItem** — id, name, estimatedPrice, priority, categoryId (optional, references Category), targetDate, dateAdded, notes, status (pending | purchased). Purchasing generates a Transaction and sets status to purchased. Kept fully independent from Goal.

**Budget** — id, categoryId, month, amount. One budget per category per month; the engine computes actual spending, remaining, percent used, and variance.

**MonthlySnapshot** — id, month, computedAt, dirty (bool), data (totalNetWorth, spendableMoney, income, expenses, savings, savingsRate, categoryBreakdown, goalProgressSummary, etc.). A materialized cache of engine output, never authoritative.

**RecurringRule** — id, transactionTemplate (type, amount, categoryId, assetId, description), frequency, nextRunDate, active (bool). Generates concrete Transactions; never appears in totals itself.

**Settings** — base currency (fixed to EGP for MVP), default views. Settings does not own the category list — Category (above) is the sole source of truth for categories. The Gemini API key is stored separately from Settings' exportable data.

## 3. Entity Relationships

- Asset 1:N Allocation (time-aware, including closed historical records); Allocation N:1 Goal (optional)
- Asset's currentValue is derived by the Financial Engine from openingBalance plus the relevant Transactions — never stored as an independently mutated balance
- Asset 1:N Transaction (income/expense via assetId)
- Asset 1:N Transaction (transfer via sourceAssetId and destinationAssetId, two references to the same entity)
- Asset has a liquidity classification (liquid | nonLiquid) that determines whether its value counts toward Spendable Money
- gold Asset 1:N GoldHoldingRecord (time-aware weight); GoldPriceRecord applies to gold Asset valuations, keyed by karat and effectiveDate
- Category 1:N Transaction
- Category 1:N Budget
- Category 1:N WishlistItem (via categoryId)
- WishlistItem 0:1 Transaction (generated on purchase)
- RecurringRule 1:N Transaction (generated by)
- MonthlySnapshot is materialized from Transaction, Asset, Allocation, Goal, GoldHoldingRecord, and GoldPriceRecord data, scoped by month

Net Worth equals the sum of every Asset's current value (liquid and non-liquid alike), with gold valued using the GoldHoldingRecord weight and GoldPriceRecord price applicable on the date in question. Transfers never change Net Worth, since money only moves between assets. Spendable Money is narrower: it only counts liquid assets (see Section 5).

## 4. Finalized Business Rules

1. A transfer Transaction never affects income/expense totals or category breakdowns.
2. A transfer draws only from an asset's spendable amount by default; it never implicitly reduces, deletes, or reassigns an Allocation. Moving allocated money to another asset requires an explicit allocation-move action, which closes the old Allocation (endDate) and opens a new one on the destination asset (startDate) with the same amount and Goal link.
3. A Goal's fundedAmount is always derived from its currently-open Allocations, never a manually typed field.
4. Allocations are never automatically shrunk when an asset's value drops. The engine instead surfaces coveredAllocation = min(totalAllocation, assetCurrentValue) and uncoveredAllocation = max(totalAllocation - assetCurrentValue, 0) as a funding gap.
5. Categories are archived, never hard-deleted, once referenced by any Transaction, Budget, or WishlistItem.
6. A WishlistItem purchase produces exactly one Transaction, which keeps its back-reference permanently, even if the WishlistItem is later deleted.
7. A closed month's MonthlySnapshot can become dirty and must be rebuildable from raw data; it is a cache, never a permanent record that overrides recalculation.
8. The Gemini API key and AI configuration are excluded from the standard financial export/backup and stored/exported separately.
9. The Financial Engine computes all derived numbers; the AI layer only consumes engine output and never performs or overrides a financial calculation.
10. A non-gold Asset's currentValue is always derived from openingBalance plus its Transactions; there is no separately mutated balance field that could drift from the ledger. Only Transactions dated on or after openingBalanceDate are included.
11. Transaction.amount is always positive; direction is carried entirely by type (income | expense | transfer), never by sign.
12. Category is the sole owner of the category list; Settings holds preferences/configuration only, not categories.
13. WishlistItem references Category via categoryId, keeping wishlist categorization consistent with the rest of the app.
14. Net Worth includes every Asset regardless of liquidity; Spendable Money includes only liquid assets. Gold and other non-liquid assets contribute 0 to Spendable Money even though they count fully toward Net Worth.
15. Gold weight is time-aware via GoldHoldingRecord, using the same close-and-open pattern as Allocation; a weight change never overwrites the prior record. A GoldHoldingRecord is not itself a Transaction.
16. An Allocation's active interval is \[startDate, endDate): active on startDate, inactive on endDate. An as-of-date query treats a date equal to endDate as no longer covered by that Allocation.
17. A Goal that is fully funded (fundedAmount >= targetAmount) reports progress capped at 100% and a required monthly contribution of 0. A Goal whose deadline has passed with fundedAmount < targetAmount reports status = overdue rather than dividing by zero or a negative remaining time.
18. "Months remaining" for a Goal is computed with a deterministic, calendar-based method (not a floating-point estimate), so required monthly contribution is reproducible.
19. savingsRate is null (displayed as N/A) whenever monthly income is zero, rather than Infinity or NaN. Savings itself may still be negative when expenses exceed income.
20. A Goal's current pace is the net change in that Goal's fundedAmount per month over the trailing window, not a count of raw Allocation record creations or closures — moving money between assets without changing total funding must not appear as a new contribution.
21. Spendable Amount is always clamped at zero: max(currentValue - activeAllocations, 0). It is never reported as negative. Any shortfall where allocations exceed an asset's current value is represented entirely by Uncovered Allocation = max(activeAllocations - currentValue, 0), the existing funding-gap mechanism, not by a negative Spendable figure.

## 5. Derived Financial Calculations

- **Non-gold Asset current value** = openingBalance + income - expenses + transfers in - transfers out, computed from Transactions dated on or after openingBalanceDate.
- **Gold Asset value as of date X** = (weight from the active GoldHoldingRecord at date X) times (price from the active GoldPriceRecord for that karat at date X).
- **Net Worth** = sum of every Asset's current value, liquid and non-liquid alike.
- **Spendable Money** (per liquid asset) = max(asset current value minus the sum of its currently-open Allocations, 0) — never negative; any shortfall is represented by Uncovered Allocation instead (below). Non-liquid assets (gold, other by default) always contribute 0 to Spendable Money, regardless of their value. Total Spendable Money = sum across liquid assets only.
- **Unallocated Non-Liquid Value** = sum over non-liquid assets of (current value minus currently-open Allocations against that asset) — e.g. gold that is not earmarked for anything.
- **Reserved/frozen money** = sum of all currently-open Allocation amounts across all assets, liquid or not.
- **Goal fundedAmount** = sum of currently-open Allocations linked to that Goal.
- **Goal fundedAmount as of date X** = sum of Allocations linked to that Goal that are active on date X under the \[startDate, endDate) rule.
- **Asset allocatedAmount as of date X** = the same as-of-date logic applied per asset instead of per goal.
- **Goal progress %** = min(fundedAmount / targetAmount, 100%) — never exceeds 100% even if overfunded.
- **Required monthly contribution** = 0 if fundedAmount >= targetAmount; otherwise (targetAmount - fundedAmount) divided by months remaining until deadline, using the deterministic calendar-based months-remaining method.
- **Goal status** = on-track / needs-attention / off-track while funding is in progress; fully-funded once fundedAmount >= targetAmount; overdue if the deadline has passed with fundedAmount < targetAmount (no division by zero, no negative remaining time).
- **Current pace** = net change in the Goal's fundedAmount per month, averaged over a trailing window (e.g. last 3 months) — based on the funded total, not a count of Allocation record creations/closures, so moving money between assets without changing total funding is not counted as a contribution.
- **On-track status** = current pace compared against required monthly contribution.
- **Coverage gap (Uncovered Allocation)** (per asset) = max(totalAllocation - assetCurrentValue, 0), surfaced whenever an asset's value drops below what is allocated against it.
- **Monthly income/expenses/savings** = sums of Transactions of each type within the month; savings = income - expenses (may be negative).
- **Savings rate** = savings / income when income > 0; null (displayed as N/A) when income is 0, never Infinity or NaN.
- **Budget variance** (per category, per month) = actual expense total for that category minus its Budget amount.
- **Unbudgeted spending** = total expenses in categories with no Budget for that month; kept distinct from budgeted spending so nothing silently falls outside analysis.

## 6. Allocation Behavior

- A normal transfer moves only spendable funds. Example: Bank has 50,000 EGP balance with 20,000 allocated, leaving 30,000 spendable; a transfer of up to 30,000 EGP out of Bank is valid, a transfer of 35,000 EGP is not.
- If spendable funds are insufficient for a requested transfer, the transfer is blocked and the UI explains why, rather than silently drawing on allocated money.
- The user can explicitly move one or more Allocations alongside a transfer. Moving an Allocation closes the existing record (assetId = source, endDate = transfer date) and opens a new one (assetId = destination, same amount and Goal link, startDate = transfer date) — the old record is preserved, not overwritten.
- Allocations may exist without a Goal (goalId optional). Valid reasons include a general emergency reserve, a tax reserve, or money simply not meant to be spent. The only requirement is a meaningful reason/description — a Goal is one possible reason, not a requirement.
- Allocations are never automatically reduced when an asset's value changes. This matters most for gold: if a 100,000 EGP allocation is backed by gold whose value later drops to 90,000 EGP, the allocation itself stays at 100,000, and the engine reports a 10,000 EGP uncovered allocation (funding gap) rather than silently shrinking the allocation.
- Reducing or releasing an Allocation follows the same close-and-open pattern: the old record is closed with an endDate at the reduction/release date, and (if any amount remains allocated) a new record opens with the smaller amount and a matching startDate. Historical allocation state is never destroyed, which is what makes "as of date X" queries possible (see Section 11).
- An Allocation's active interval is \[startDate, endDate): it is active on its startDate and no longer active on its endDate. When an allocation moves or changes (Sep 1 – Oct 10 closed, Oct 10 – open opened), the old record is not active on October 10; the new one is — there is never a moment where both or neither cover that date.

## 7. MonthlySnapshot Behavior

Financial state is cumulative, so dirtying is not limited to the changed month. If a historical Transaction, Allocation, Asset opening state (openingBalance/openingBalanceDate), GoldPriceRecord, or GoldHoldingRecord affecting a given month is created, edited, or deleted, that month's MonthlySnapshot AND every later MonthlySnapshot are marked dirty — not just the one directly touched. Example: a gold price correction effective September 15 dirties the September snapshot and every snapshot from October onward; a gold-weight correction effective October 1 dirties October onward, since each month's figures build on the one before it.

Lazy rebuild strategy (unchanged):

Lazy rebuild strategy (unchanged):

1. When historical data (a Transaction, Allocation, or Asset dated within an already-snapshotted month) changes, mark that month's MonthlySnapshot as dirty. No immediate rebuild happens at write time.
2. When that month is next requested for display or analysis, the engine detects dirty = true.
3. The engine recalculates the snapshot from raw data.
4. The cached snapshot is replaced with the rebuilt result and dirty is cleared.

An explicit "Recalculate History" action will eventually let all historical snapshots be rebuilt on demand. This keeps writes simple and keeps the snapshot clearly a cache rather than a source of truth.

## 8. RecurringRule Behavior

Backfill by default. If the app was closed when one or more scheduled occurrences were due, the next launch generates the missed Transactions using their original scheduled dates, not the date the app happened to reopen. Example: a monthly salary rule scheduled for the 1st, with the app unopened in July and August and reopened on September 10, generates transactions dated July 1, August 1, and September 1.

Generated transactions are ordinary Transactions: reviewable, editable, and deletable like any manually entered one. A future enhancement may allow per-rule forward-only behavior, but backfill is the MVP default.

## 9. Budget Behavior

A Budget is a monthly spending limit per expense category (e.g. Food: 4,000 EGP for September 2026), not a global monthly cap. For each budgeted category, the engine tracks actual spending, remaining amount, percent used, and variance (actual minus budget).

Unbudgeted spending is never allowed to disappear from analysis. For each month the engine distinguishes budgeted spending, unbudgeted spending (expenses in categories with no Budget that month), and total spending, so the dashboard can show all three explicitly rather than treating unbudgeted variance as zero. A global, non-per-category budget cap is deferred past the MVP.

## 10. Gold Valuation Behavior

For the MVP, both gold prices and gold weight are entered manually, and both are kept as history rather than a single latest value. Price is a GoldPriceRecord (karat, pricePerGram, effectiveDate, createdAt); weight is a GoldHoldingRecord (assetId, weightGrams, startDate, optional endDate, createdAt), closed and reopened the same way an Allocation is when the owned weight changes. A gold Asset's currentValue as of any date is derived as the weight from the applicable GoldHoldingRecord times the price from the applicable GoldPriceRecord for that karat, both evaluated as of that date — never a separately stored, manually duplicated value, and never simply "the latest weight" or "the latest price" when valuing a past date. This is what lets a September net-worth figure stay correct even after October's weight or price is entered.

Because gold's EGP value can change without the user's ownership changing (price) or the user's ownership can change directly (weight, e.g. a sale), any Allocation backed by a gold Asset is exposed to the coverage-gap rule in Section 6: a drop in the applicable price or weight can push an Allocation from fully covered to partially uncovered, and the engine must surface that gap rather than silently adjusting the Allocation. Automatic gold-price lookup and automatic gold buy/sell workflows remain deferred, future enhancements; the current price and current weight are simply the latest applicable GoldPriceRecord and GoldHoldingRecord.

## 11. Historical-Data Behavior

Four mechanisms exist specifically so the app can answer "what was true as of a past date" correctly, not just "what is true now":

- **Cascading dirty snapshots** (Section 7): correcting historical Transaction, Allocation, Asset opening state, GoldPriceRecord, or GoldHoldingRecord data dirties the affected month and every later month, since each month's figures build on the one before it.
- **Historical gold pricing** (Section 10, GoldPriceRecord): a gold Asset is priced using the value applicable on the date in question, so an old snapshot never gets silently repriced by a later price entry.
- **Historical gold weight** (Section 10, GoldHoldingRecord): a gold Asset's owned weight is likewise looked up as of the date in question, so a sale recorded later never changes how much gold September thought it had.
- **Time-aware Allocations** (Section 6): changing, moving, reducing, or releasing an Allocation closes the old record with an endDate and opens a new one on a \[startDate, endDate) interval, rather than mutating history in place.

Together these let the Financial Engine compute both current-state values (e.g. Goal fundedAmount, Net Worth) and as-of-date values (e.g. Goal fundedAmount as of date X, Asset allocatedAmount as of date X, or gold Asset value as of date X) from the same underlying data, without a separate historical data store.

## 12. Data Ownership, Export/Import, and Gemini API Key Handling

The complete financial dataset (Transactions, Categories, Assets, Allocations, Goals, WishlistItems, Budgets, MonthlySnapshots, RecurringRules, and non-AI Settings) must be exportable to a portable, structured file (JSON is the likely format) and importable back, including on a different device or browser. The export must carry a schema version, and imports must validate the incoming data, detect incompatible versions, and migrate older schemas where possible without silent data loss.

The Gemini API key and any AI configuration are excluded from the standard financial export/backup file. If the key needs to be backed up at all, it is handled as a separate, clearly-labeled artifact, never bundled into the financial data export. The core application remains fully functional with no Gemini key present.

## 13. AI Boundaries

Hierarchy: Local Data → Financial Engine → Metrics/Business Rules → UI/Dashboard, and optionally, Metrics/Business Rules → AI Context Builder → Gemini → Natural-language analysis.

The AI (Gemini, optional) may explain, analyze, identify patterns, answer questions, and suggest actions — but it never computes or overrides a financial value, and it never silently modifies application state. Any AI-suggested action that would change data (e.g. adding an expense) requires explicit user confirmation before it is applied. The AI context sent to Gemini should be a structured, purpose-built subset of the calculated metrics for the requested analysis, not the entire raw dataset.

## 14. MVP Boundaries

**In scope for MVP:** the full entity model in Section 2, including GoldPriceRecord and GoldHoldingRecord; single-currency (EGP) transactions, transfers, and time-aware Allocations on a \[startDate, endDate) interval; derived (not manually mutated) Asset balances with explicit openingBalance/openingBalanceDate semantics; Asset liquidity classification separating Net Worth from Spendable Money, plus Unallocated Non-Liquid Value; manual, history-tracked gold pricing and weight; per-category monthly Budgets with an unbudgeted-spending rollup; Goals with derived progress, defined fully-funded/overdue edge cases, deterministic months-remaining, and as-of-date progress; Wishlist with purchase-to-Transaction flow, referencing Category via categoryId; lazily-rebuilt MonthlySnapshots with cascading dirty propagation across later months, triggered by Transaction, Allocation, Asset opening state, GoldPriceRecord, or GoldHoldingRecord changes; RecurringRule with backfill; local export/import with schema versioning.

**Explicitly deferred, not in MVP:**

- Multi-currency support and exchange rates
- Automatic gold-price lookup (API-based)
- A Liability/debt entity — only introduced if a real need arises
- A global (non-per-category) monthly spending cap
- Voice input
- Gemini AI integration (architected for, not built yet)
- What-if/financial simulation
- Per-RecurringRule forward-only vs backfill configuration (backfill is the only MVP behavior)
- Automatic gold buy/sell workflows and automatic linking between gold purchases/sales and cash Transactions
